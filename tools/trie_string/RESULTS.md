# TrieString 検証・計測

VM101 (Linux amd64)、2026-10-24。独立したローカルcheckoutの
`trie-string-handles` ブランチ、基点 `66de9ab369c0ab6451dd3caad1afed7ce7c0024d`。
既存checkoutの変更を取り込まず、以下の検証・計測を独立して実施した。

## 正しさ

Nim **1.6.20 / 2.2.4 / 2.2.6**、**C / C++**、**debug / release** の12通り。
それぞれ内部不変条件を含む本体テストと、通常のimportで公開APIを使うテストを実行。
公開 `lcp`・変換・`trie[node,index]` による一点取得・LCP節点・prefix取得を含む最終APIで24実行を再検証した。
再実行時の結果は同じディレクトリの `validation.txt` に保存する（生成ログはGit管理対象外）。

- 完全二分Trie（1023節点）の **1,046,529組** を実際の文字列比較と照合。
- 3 seed・合計60,000回の追加、**600,000組** の乱択文字列比較。
- Array/Table両版の **200,000組** の比較を文字列オラクルと照合。
- 全256byte、NUL、非ASCII、重複追加、接頭辞、根、未初期化、不正ハンドル、範囲外文字。
- 262,145段の2本の鎖、途中分岐、全深さでのskewブロック不変条件。
- 深さ0..2048の全祖先対象と、262,145段の鎖の全祖先対象。
  この測定で最大探索歩数は **36**。実装内部の祖先探索結果も全対象で検証。
- 両版で共通接頭辞の深さをskew-rank境界付近に置き、その下に4097要素の別々のsuffixを作る。
- 汎用整数、意図的に同じhashを返す要素、呼び出し側で定義した要素演算子。
- `lcp` は全1,046,529組と600,000乱択組をbrute文字列LCPと照合し、
  Array/Tableの200,000組でも検証。両版で同一ID、根、接頭辞、長い共通接頭辞、
  不正ID（両引数と同一不正ID）、未初期化を検査。公開import経由のLCPも検査。
- `toString` / `toSeq` / `[]` / `prefix` / `lcpNode` は両char版の全256byte、
  各3,000回の乱択追加・各15,000組のLCP節点オラクル、8,193段の鎖で検査。
  汎用int版でも3,000回の追加と復元・全位置取得・全prefix・LCP節点をbrute列と照合。
  空列、同一ID、接頭辞、根、分岐、不正ハンドル、負数・上限外の位置/長さを検査。
  navigationが節点を追加しないことと、prefixが既存の親IDを返すことも確認。

C++の `g++` は通常のPATHになかったため、既存のGCC 13 toolchain wrapperを利用した。
外部パッケージへの依存追加やライブラリ全体のC移植は不要だった。

## 計測条件

Nim 2.2.6、C、`-d:release`、デフォルトORC。各行を別プロセスで1回測定。
時間は `cpuTime()` の秒数、メモリは `/usr/bin/time -f rss_kib=%M` の最大RSS。
RSSには入力ハンドル配列、ランタイム、seq/Tableの余剰容量・再確保時のピークも含む。
最小限の節点ペイロードだけのサイズではない。
再実行時の計測ログ（削除・重複追加・分岐形状も含む）は `benchmark.txt`（Git管理対象外）。
計測値はAPI改名前の値を保持し、出力ラベルのみ `add_s` / `pop_s` に統一した。
一点取得を `[]` に統一した後のベンチマーク呼び出しも4版でコンパイル・実行確認した。
上記計測値は追加・親取得・辞書順比較の値であり、LCPの性能計測値ではない。

2本の長い鎖を作り、深さを変えながら1,000,000回比較する結果:

| 版 | 節点数（根を含む） | 構築 秒 | 100万比較 秒 | 最大RSS KiB |
|---|---:|---:|---:|---:|
| Table | 100,001 | 0.0370 | 0.4726 | 23,536 |
| Table | 200,001 | 0.0751 | 0.5707 | 48,888 |
| Table | 400,001 | 0.1500 | 0.7261 | 83,832 |
| Table | 800,001 | 0.3305 | 0.9369 | 175,224 |
| Array σ=2 | 100,001 | 0.0156 | 0.4848 | 11,252 |
| Array σ=2 | 200,001 | 0.0307 | 0.6170 | 23,924 |
| Array σ=2 | 400,001 | 0.0576 | 0.7633 | 51,188 |
| Array σ=2 | 800,001 | 0.1023 | 0.9679 | 84,596 |
| Array σ=26 | 100,001 | 0.0697 | 0.4753 | 60,788 |
| Array σ=26 | 800,001 | 0.5624 | 0.8977 | 504,692 |
| Array σ=256 | 25,001 | 0.1218 | 0.3128 | 116,852 |
| Array σ=256 | 50,001 | 0.3451 | 0.3934 | 331,504 |
| Array σ=256 | 100,001 | 0.5979 | 0.4775 | 579,188 |

800,001節点の鎖で400,000回の親取得は Table **0.00312秒**、Array σ=2 **0.00330秒**。
同数の重複追加は Table **0.04535秒**、Array σ=2 **0.00310秒**。
400,001節点の二分木形状では構築がTable **0.1479秒**、Array σ=2 **0.0597秒**、
100万比較がそれぞれ **0.2252秒 / 0.2145秒**。

固定σで構築時間・メモリが概ね線形に増える様子を確認できる。
ただし再確保閾値・キャッシュ・実行時負荷により比率は変動する。
σ=256の配列は空間定数が非常に大きいので、疎なbyte TrieではTable版が有利。
実測は漸近境界の証明ではなく、証明は `docs/str/trie_string.md` に記載した。

## 再実行

リポジトリの根で、使用する既存コンパイラのパスを指定する。
`g++` がPATHに必要。以下のコンパイラパスは各環境に合わせて置き換える。

```sh
python3 tools/trie_string/validate.py \
  /path/to/nim-1.6.20/bin/nim \
  /path/to/nim-2.2.4/bin/nim \
  /path/to/nim-2.2.6/bin/nim

python3 tools/trie_string/benchmark.py /path/to/nim-2.2.6/bin/nim
```

単体実行例:

```sh
nim c -r --path:src -d:release --out:/tmp/trie-test src/verify/str/trie_string_test.nim
nim c --path:src -d:release -d:array2 --out:/tmp/trie-bench src/verify/str/trie_string_benchmark.nim
/usr/bin/time -f 'rss_kib=%M' /tmp/trie-bench 400000 chains
```
